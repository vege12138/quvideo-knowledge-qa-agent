# 需求规格 v1.6

目标用户为查询内部制度或产品规则的员工。知识全部来自虚构的星映科技合成资料。根目录运行说明与本规格遵守 [考核原文](assignment.md)。

| ID | 要求 | 验收证据 |
|---|---|---|
| R01 | 仅检索运行知识库，保留版本、范围和引用锚点 | 检索/读取单测；开发集证据 |
| R02 | 模型决定工具、参数与后续动作，形成真实循环 | 真实执行 Trace |
| R03 | 回答附本轮读取的文档 ID、片段 ID 与原文；无依据不作确定结论 | 引用校验测试；语义评估 |
| R04 | 同范围规则冲突时查证与澄清，不仅按日期裁决；不同套餐不误判冲突 | conflict 场景与变更实验 |
| R05 | 资料未覆盖时说明缺口 | out_of_scope 场景 |
| R06 | 支持口语改写和基于历史的追问，每轮重新查证 | paraphrase / follow_up 场景 |
| R07 | 工具故障可观察，恢复和持续失败状态明确 | 故障注入与恢复 Trace |
| R08 | 限制模型次数、工具次数和超时；耗尽明确未完成 | 预算/超时测试 |
| R09 | 阶段 4 有真实单轮 CLI，JSON 与 Trace 输出；Mock 明示边界 | MVP 三组真实运行 |
| R10 | 输入、输出、测试、五份文档和 AI 使用记录可追踪 | examples、评估报告、文档 |
| R11 | 网页复用服务，显示引用与状态，会话隔离 | HTTP 与浏览器检查 |
| R12 | 运行时不访问评估答案/关系标注，不暴露凭证 | 文件访问边界、忽略规则、提交检查 |

统一结果：answer、status、clarification_reason、citations、gaps、run_id、reason_code、trace、metrics、mode。status 为 answered / clarification_required / insufficient_evidence / tool_error / incomplete。引用含 doc_id / chunk_id / quote。模型或工具失败不能冒充成功，只有规则标签一致不算语义验收通过。

SDD 规则：每阶段先写计划与验收，再实现并回填真实证据；未执行项目明确标为未执行。开发集可调优，保留测试集在方案冻结后运行；若用测试集修改实现，应披露。

v1.1 验收补充（首次评估发现）：R03 要求逐条保留来源，不把单份文档规定归属于双方；R07 故障用例必须在 Trace 中实际出现指定工具/文档的错误与恢复，未知注入模式应报配置错误而非静默失效。首次保留集参与了故障修复，后续结果标记为回归。

## v1.2：已批准的收尾规格

本次规格先于对应收尾实现更新。早期实现与评估历史保持原样，不追溯声称所有已有代码均按本版本开发。阶段 4 已有真实 CLI MVP；本轮完成阶段 5 的失败边界与澄清校验、阶段 6 的证据和文档，并验证已有本地网页。

### R07、R08：连续工具失败硬边界

- `search_documents` 的所有查询共用一个失败计数，修改 query 不清零。
- `read_document` 按 doc_id 计数；切换 chunk 或成功读取其他文档，不清零该文档的失败次数。
- `timeout` 与 `tool_exception` 合并计数；同一个计数键成功后清零。`invalid_request` 不计入连续故障，但调用仍计入工具总预算。
- 第三次失败必须先写入 Trace 和工具调用计数，再立即以 `status=tool_error`、`reason_code=tool_failure_limit` 结束，并跳过同批剩余工具。此前由模型自主决定重试、改写查询、补查或停止。
- 8 次模型、12 次工具、请求超时与运行总时限继续生效；先达到哪一个结束条件，就按该条件结束。校验修正和重试不另开预算。

### R03、R04、R06：明确澄清原因与证据门槛

- 新增 `clarification_reason: conflict | missing_context | null`，默认 null，以便读取旧 JSON。兼容旧数据不代表免除新回答的验收规则。
- 新的 `clarification_required` 必须明确非空 reason；其他状态必须为 null。
- `conflict` 至少引用两个不同的 `(doc_id, chunk_id)`，可来自同一文档。每个引用都必须来自本轮实际读取的原文，并通过精确子串校验。该结构门槛仍不能替代“引用真的相互矛盾”的语义核查。
- `missing_context` 可以不含引用，但 gaps 必须具体说明需补充的范围或上下文；不能用空泛提示代替需要明确的信息。
- 校验失败反馈模型修正，修正计入既有模型次数和运行时间预算；不能原样标记成功。

### R10—R12：证据、复核与交付约定

- 保留初次评估及 v2 原始输出；新评估写入独立目录，完成 12 道开发题、12 道已参与修复的测试回归题、4 个文档变更实验。
- 自动结构检查与逐题语义复核分别报告。复核由 AI 辅助完成，不新增评审模型，不冒充用户或独立人工确认。
- 独立 review.json 以 case_id、run_id 和输出 SHA-256 绑定证据，记录 criteria、verdict 与依据；输出改变必须重新复核，过期复核不得计为通过。
- 正式记录当前完整测试、干净环境安装与运行、网页接口及视觉检查。未执行或受阻项目明确标记，不用 HTTP 通过替代视觉检查。
- 补齐五份必需文档和需求证据索引，如实披露保留测试参与修复、已知缺陷与 AI 使用范围，不补造个人贡献或精确用时。
- 本轮交付本地可提交包并创建本地 Git commit，记录真实 SHA；不 push 或部署远程服务。提交前检查敏感数据、忽略规则和实际纳入的文件。

验收用例与证据索引见 [评估文档](03-evaluation.md)；收尾任务见 [阶段 5](phases/05-complete-behavior.md) 与 [阶段 6](phases/06-evaluation-delivery.md)。未产出证据前，规格中的约定均不能被当作已通过结果。

## v1.3：R04 当前问题范围与状态

首个真实开发回归发现：用户只问预扣积分数量，模型虽然给出正确数量，却扩展到退款时间冲突并返回 clarification_required。失败证据保留在 examples/evaluation/final-20261031/dev/C03.json。

- 回答和最终状态只针对当前所问属性与范围。其他事项的冲突，不自动使当前已有充分一致证据的事项变为冲突。
- 模型可以读取相关原文并发现其他差异，但不应把用户未问且不影响当前结论的争议加入最终回答或据此改变状态。
- 当前问题证据一致且充分时返回 answered；只有所问事项无法调和时才以 conflict 澄清。不能因知识库存在任意冲突就统一澄清。
- 验收覆盖同一主题的不同属性：一致属性正常回答，真正冲突的属性仍列双方原文并澄清。这是通用业务约束，不按题号或文档硬编码答案。

本次先更新规格再修订提示，重新执行完整确定性测试和 28 题真实评估；新输出位于 examples/evaluation/final-20261031-r2/，初次 final-20261031/dev 保留原样。

## v1.4：R03 原文明示与阅读后缺失的信息

r2 开发集 H03 的数字、冲突判断和引用子串正确，但把“所读资料没有提供优先级或废止关系”表述为“原文明示没有说明”。这将阅读后的缺失判断错误归为文档直接声明。原始输出保留在 examples/evaluation/final-20261031-r2/dev/H03.json，citation_support 复核失败。

- 区分文档直接写明的规定与阅读后未发现的信息。只有原文确实作出该声明时，才可使用“原文明确规定/明示”等来源归属表述。
- 原文没有提供的信息，只能表述为“所读资料未提供……”等受当前已读范围限制的观察，不能把缺失伪称文档的直接声明。
- 版本、有效状态等元信息若未被所引原文陈述，不能称为引用片段中的原话；结论必须准确区分原文、元信息与阅读观察。
- 复核除核查数字和 quote 子串外，也检查答案中关于证据来源的措辞是否获得支持。该规则适用于所有主题，不按题号修补答案。
- 每个操作、位置与对象的关系都须得到原文支持；不能把分别成立的信息拼成文档未记载的界面操作。只回答当前事项，避免附加用户未问且非必要的操作建议。

r2 回归 K04 另将“积分流水可查积分变动”和“确认任务状态”拼成“去积分流水确认是否失败”，原文没有支持该操作位置与对象的关系。此例也记录 citation_support 失败并保留原输出。修复应约束通用证据归属，不新增题目特殊分支。

先更新此规格，再修订通用提示并重新执行 28 题真实评估。最终新目录为 examples/evaluation/final-20261101/，测试记录为 examples/final-20261101/tests.xml；r2 结果和复核保留，不回写成通过。


## v1.5：R03/R04/R08 回答完成状态与缺口一致

2026-11-01 收尾增量，先记录规格再实现。保留 final-20261101/dev/C03.json 的失败原件。

- `answered` 表示当前问题已经完整回答，因此 `gaps` 必须为空；存在阻止当前问题完成的缺口，应按实际原因澄清或说明资料不足。
- 校验发现 answered 带 gaps 时，将错误反馈模型：重新核对当前问题，删除无关事项及其缺口；若缺口确实阻止回答则改为相应状态。运行时不得静默清空字段或替模型删改正文。修正沿用原调用预算。
- 最终正文的每一条业务规定均须由 citations 中的原文支持；只读取过相关资料并不等于已提供引用。避免附加用户未问的其他事项。此语义要求仍需逐题复核，空 gaps 不能证明正文无偏题。
- 验收：旧 C03 输出触发校验；模型修正后通过；重复无效输出达到预算返回 incomplete。重跑完整确定性测试及 28 题真实评估；分别复核预扣数量与退款冲突，保留失败，不挑选运行结果。
- 网页验收覆盖实际页面提交、等待/禁用、引用与查证过程、新会话、错误提示。若桌面浏览器工具不可用，允许使用本地浏览器自动化检查同一静态页面，明确记录浏览器和测试方式。
